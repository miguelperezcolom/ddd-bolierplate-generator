## Hexagonal Architecture

All code generated by Modux follows **Hexagonal Architecture** (also known as Ports & Adapters). The domain is at the centre, and all external concerns (databases, messaging, UI) are adapters that plug in through well-defined port interfaces.

```
┌─────────────────────────────────────────────┐
│                   Adapters                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │  UI/API  │  │  Kafka   │  │   JPA    │  │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  │
│       │              │              │        │
│  ┌────▼──────────────▼──────────────▼─────┐ │
│  │           Application Layer            │ │
│  │  Use Cases │ Query Services │ Ports    │ │
│  └────────────────────┬───────────────────┘ │
│                        │                    │
│  ┌─────────────────────▼───────────────────┐│
│  │              Domain Layer               ││
│  │  Aggregates │ Entities │ Value Objects  ││
│  │  Domain Events │ Domain Services        ││
│  └─────────────────────────────────────────┘│
└─────────────────────────────────────────────┘
```

### Domain Layer

The innermost layer. Contains pure business logic with no external dependencies.

| Component | Description |
|---|---|
| **Aggregate Root** | Central entity controlling its consistency boundary |
| **Entity** | Domain object with identity within an aggregate |
| **Value Object** | Immutable typed descriptor (e.g. `Email`, `BookingId`) |
| **Domain Event** | Record of something that happened |
| **Domain Service** | Business logic that doesn't belong to a single aggregate |

### Application Layer

Orchestrates domain objects to fulfil use cases. Depends on the domain but not on infrastructure.

| Component | Description |
|---|---|
| **Use Case** | Handles a single command (create, update, delete, custom) |
| **Query Service** | Assembles read results from the persistence layer |
| **Repository (port)** | Interface for aggregate persistence |
| **DTO** | Data Transfer Object for input/output |

### Infrastructure Layer

Implements the ports defined in the application layer.

| Component | Description |
|---|---|
| **JPA Entity** | Database representation of an aggregate |
| **DB Repository** | Implements the domain repository port using Spring Data |
| **UI Adapter** | Wires the CRUD UI to the application layer use cases |
| **Kafka Consumer** | Implements subscriptions and saga steps |
| **HTTP Client** | Implements gateway ports using RestTemplate/WebClient |

## Package structure

```
com.example.booking.
└── bookings/
    ├── domain/
    │   └── aggregates/
    │       └── booking/
    │           ├── Booking.java
    │           ├── vo/
    │           │   ├── BookingId.java
    │           │   └── BookingReference.java
    │           └── events/
    │               └── BookingConfirmed.java
    ├── application/
    │   ├── usecases/
    │   │   ├── CreateBookingUseCase.java
    │   │   ├── UpdateBookingUseCase.java
    │   │   └── ConfirmBookingUseCase.java
    │   ├── query/
    │   │   ├── BookingQueryService.java
    │   │   ├── BookingDto.java
    │   │   └── BookingRow.java
    │   └── out/
    │       └── BookingRepository.java
    └── infra/
        ├── in/
        │   └── ui/
        │       ├── BookingCrudAdapter.java
        │       ├── BookingCrudOrchestrator.java
        │       └── BookingViewModel.java
        └── out/
            └── persistence/
                ├── BookingEntity.java
                ├── BookingEntityRepository.java
                ├── BookingDBRepository.java
                └── BookingDBQueryService.java
```

## Dependency rules

| Layer | Can depend on |
|---|---|
| Domain | Nothing |
| Application | Domain only |
| Infrastructure | Application + Domain |

This ensures that business logic is never coupled to infrastructure details.

---

## CQRS split

Modux enforces a soft CQRS split:

- **Write side**: Use cases receive commands, apply them to aggregates via the repository, and emit events
- **Read side**: Query services read from persistence directly (bypassing the domain) and return flat DTOs

This allows the read and write models to evolve independently.
